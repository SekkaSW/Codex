# Setup message conversation correction

Focused follow-up to the completed Discord dashboard UX overhaul, September 18, 2026.

1. **Starting branch/HEAD:** clean `main` at `06942e95d8b58f49efbf96944868a4d169b087ff` (`Improve Discord setup and interaction UX`). Completed phases and that commit were preserved.
2. **Final branch/HEAD:** `setup-message-conversation`; the final HEAD is the commit containing this report. Its full SHA is reported in the task's final response.
3. **Commit:** `Use conversational message replies for server setup`, authored with this repository's existing local SekkaSW identity. No global Git configuration changes.
4. **Conversation boundary:** only the draft owner, in the bound guild/channel, while a matching text question is active. A private setup thread accepts the next owner message newer than the prompt; fallback requires a direct reply to the current prompt. Explicit replies to older messages are ignored in either mode. Ordinary guild chat is not parsed or sent to the setup repository.
5. **Literal message fields:** organization name, namespace, confidentiality marker, rank and branch names, duty display name, assignment group/entry names, and custom managed channel/category/forum creation names. Existing Detailed Editor text/create forms also use messages. No unsupported description fields were invented. Ordinary guided text questions do not require a modal-opening button.
6. **Selectors/buttons retained:** role and destination selectors, existing entity lists and pagination, permission tiers, module choices, Yes/No, Done, Add Another, Back, optional Skip, Cancel, Keep Current, section editing, Review and Confirm Setup. The 20 dashboards and non-setup forms remain intact.
7. **Intent/runtime:** reuses the existing Message Content intent and the single MessageCreate listener, alongside unchanged bot-message legacy bridge intake. Setup checks client intent and Discord application entitlement flags; missing/unverifiable access gives actionable instructions. The existing per-guild operation queue also serializes setup replies. Capture of the prompt revision at event arrival prevents a queued burst from answering later questions.
8. **Thread/channel behavior:** creates an invite-disabled private thread when permissions allow, adds its owner and persists its binding in draft JSON. Reuses or reopens it on later invocations. Otherwise it uses a tightly scoped channel fallback. An uncertain thread creation is recorded and not blindly repeated. Completion/cancellation attempts to archive the private thread; it never deletes transcripts or changes channel overwrites.
9. **Resume/restart:** accepted values, guided progress and pending Detailed Editor text prompts survive through the existing durable draft. After process restart, `/server setup` offers Resume/Start Over/View Progress/Cancel. Resume reconstructs the saved question and issues a fresh fenced prompt. Start Over remains explicit and resets only the draft from saved production configuration, reusing the conversation. A failed send or prompt-binding save leaves prior accepted values intact and orphan prompts inert.
10. **Safeguards:** fresh Discord Administrator checks, owner/guild/channel/prompt identity, expected-question matching, expiry, durable revision checks, bot/webhook exclusion, text validation and final review remain enforced. Message answers cannot be submitted through forged modal or selector interactions. Mentions are suppressed. Error replies use the existing friendly error sanitizer. Back shows retained values; branch-name replacement preserves the branch identity. No accepted configuration lives only in memory.
11. **Tests:** 155 passing, zero failed/skipped/cancelled: all original 108 plus 47 message-conversation tests. Coverage includes the requested text fields and controls, non-owner/unrelated/wrong-channel traffic, direct replies, expiry, permission loss, stale/burst replies, resume, private thread fallback/reuse/archival, detailed text edits, failure recovery and real SQL draft-payload persistence/revision enforcement.
12. **Validation:** `npm install` succeeded with dependencies already up to date; `npm test`, `npm run lint`, `npm run build` and `git diff --check` passed. Command/event routing and stale components were reviewed. The final staged review excludes credentials, environment files, generated output and unrelated files.

Resume is required to re-arm message capture after a process restart. Only one bot writer per guild is supported, as before.
